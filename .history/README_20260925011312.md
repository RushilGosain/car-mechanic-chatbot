An AI-powered car mechanic chatbot that helps users describe vehicle problems, answers rule-based follow-up questions, analyzes uploaded images when useful, generates an AI-assisted diagnosis using Google Gemini, and allows users to request a mechanic booking.

## Project Overview

The application combines a **Next.js frontend**, **Django REST Framework backend**, and **Google Gemini AI**.

The chatbot does not call Gemini for every message. The conversation flow is handled primarily by deterministic Python rules. Gemini is used where AI adds genuine value:

- Synthesizing the complete conversation into a diagnosis
- Analyzing uploaded vehicle images
- Producing probable causes, recommended repair/service action, and confidence

How the Application Works
1. User starts a conversation

The user describes a car problem, for example:

"My car makes a clicking noise when I turn the steering wheel."

The frontend sends the message to:

POST /api/chat/
2. Backend validates the conversation

The Django backend checks whether the message is related to a car problem.

It can:

Recognize greetings
Reject unrelated questions
Detect symptom categories
Start the appropriate follow-up flow
3. Follow-up questions

The backend uses rules.py to ask relevant questions.

For example:

User:
My car makes a noise when turning.

Bot:
Does the noise happen when the car is moving, stationary, or both?

User:
Mostly when moving.

Bot:
Is the noise more like a clicking, grinding, or knocking sound?

These questions are handled by normal Python logic rather than making an unnecessary AI request for every message.

4. Media upload

Users can upload:

Images
Audio
Video

Images can be analyzed using Gemini's vision capabilities.

Audio and video are stored with the conversation and can be reviewed by a technician.

5. Diagnosis

Once enough information has been collected, the frontend requests:

POST /api/diagnosis/

The backend combines:

User messages
Bot responses
Uploaded media notes

and sends the relevant context to Gemini.

Gemini returns:

Summary
Probable causes
Suggested repair
Confidence level
6. Mechanic booking

After diagnosis, the user can provide:

Name
Phone number
Preferred date
Additional notes

The booking is stored by Django.

API Documentation

Base URL for local development:

http://127.0.0.1:8000/api
1. Chat
Endpoint
POST /api/chat/
Purpose

Sends a user message to the chatbot and receives the next response.

Request
{
  "conversation_id": null,
  "message": "My car is overheating."
}

For a new conversation, conversation_id can be null or omitted.

For an existing conversation:

{
  "conversation_id": "conversation-uuid",
  "message": "It happens after driving for about 20 minutes."
}
Response
{
  "conversation_id": "conversation-uuid",
  "bot_reply": "Does the temperature warning light come on?",
  "ready_for_diagnosis": false
}

When enough information has been collected:

{
  "conversation_id": "conversation-uuid",
  "bot_reply": "Thanks, that's enough detail for me to work with. Shall I go ahead and put together a diagnosis?",
  "ready_for_diagnosis": true
}
2. Upload Media
Endpoint
POST /api/upload/
Purpose

Uploads an image, audio file, or video associated with a conversation.

Content Type
multipart/form-data
Fields
conversation_id
media_type
file
Example
conversation_id = 123e4567-e89b-12d3-a456-426614174000
media_type = image
file = dashboard-warning.jpg
Supported media types
image
audio
video
Response

The API returns the created media upload, including its conversation, media type, file information, and analysis note.

For images, the analysis note may contain Gemini's visual observation.

3. Generate Diagnosis
Endpoint
POST /api/diagnosis/
Purpose

Generates the final diagnosis using the complete conversation and available media analysis.

Request
{
  "conversation_id": "conversation-uuid"
}
Response

The diagnosis contains information such as:

{
  "summary": "The vehicle may have an issue related to its cooling system.",
  "probable_causes": "Low coolant\nFaulty thermostat\nCooling fan problem",
  "suggested_repair": "Inspect the cooling system and check coolant level, thermostat operation, and radiator fan.",
  "confidence": "medium",
  "used_ai": true,
  "book_recommended": true
}
4. Create Mechanic Booking
Endpoint
POST /api/booking/
Request
{
  "conversation_id": "conversation-uuid",
  "customer_name": "John Doe",
  "phone_number": "9876543210",
  "preferred_date": "2026-10-01",
  "notes": "Please contact me after 5 PM."
}
Response

Returns the created booking with its booking ID and associated conversation/diagnosis information.

5. Get Booking
Endpoint
GET /api/booking/<id>/
Example
GET /api/booking/1/
Purpose

Retrieves details of a specific mechanic booking.

6. Get Conversation
Endpoint
GET /api/conversation/<conversation_id>/
Purpose

Retrieves a conversation and its stored messages.

Deployment
Frontend — Netlify

The frontend can be deployed through Netlify.

Set the production environment variable:

NEXT_PUBLIC_API_BASE_URL=<YOUR_RENDER_BACKEND_API_URL>/api

The frontend must use the deployed Render backend rather than:

http://127.0.0.1:8000/api
Backend — Render

The Django backend can be deployed on Render using a production WSGI server such as Gunicorn.

The production environment should contain:

GEMINI_API_KEY=<your-key>

The Django deployment should also be configured with the appropriate production:

DEBUG
ALLOWED_HOSTS
CORS settings
static/media configuration
database configuration

After deployment, the Render URL becomes the backend API base URL used by the Netlify frontend.

Security Notes
API keys are stored in environment variables.
.env and .env.local should not be committed.
node_modules/, Python virtual environments, SQLite runtime files, and generated media should be excluded where appropriate.
The Gemini API key should never be hard-coded into frontend JavaScript.
Production deployment should use DEBUG=False.
