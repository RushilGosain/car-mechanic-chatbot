## Overview

An AI-powered car mechanic chatbot that helps users describe vehicle problems, answers rule-based follow-up questions, analyzes uploaded images when useful, generates an AI-assisted diagnosis using **Google Gemini**, and lets users request a mechanic booking.

The app combines a **Next.js frontend**, a **Django REST Framework backend**, and **Google Gemini AI**.

The chatbot does **not** call Gemini for every message. The conversation flow is handled primarily by deterministic Python rules, and Gemini is used only where AI adds real value:

- Synthesizing the complete conversation into a diagnosis
- Analyzing uploaded vehicle images
- Producing probable causes, a recommended repair or service action, and a confidence level

This keeps the conversation predictable, fast, and inexpensive.

### Main Flow

```text
User
  │
  ▼
Next.js Frontend
  │
  ▼
Django REST API
  │
  ├── Rule-based topic detection

  │

  └── Image analysis
  │
  ▼
Tailored Diagnosis
  │
  ▼
Mechanic Booking
```

## How It Works

### 1. User starts a conversation

The user describes a car problem, for example:

> "My car makes a clicking noise when I turn the steering wheel."

The frontend sends the message to `POST /api/chat/`.

### 2. Backend validates the conversation

The Django backend checks whether the message is related to a car problem. It can:

- Recognize greetings
- Reject unrelated questions
- Detect symptom categories
- Start the appropriate follow-up flow

### 3. Follow-up questions

The backend uses `rules.py` to ask relevant questions.

> **User:** My car makes a noise when turning.
> **Bot:** Does the noise happen when the car is moving, stationary, or both?
> **User:** Mostly when moving.
> **Bot:** Is the noise more like a clicking, grinding, or knocking sound?

These questions are handled by plain Python logic rather than an unnecessary AI request for every message.

### 4. Media upload

Users can upload images, audio, and video.

- **Images** are analyzed with Gemini's vision capabilities.
- **Audio and video** are stored with the conversation so a technician can review them.

### 5. Diagnosis

Once enough information has been collected, the frontend requests `POST /api/diagnosis/`. The backend combines the user messages, bot responses, and uploaded media notes, and sends the relevant context to Gemini. Gemini returns:

- Summary
- Probable causes
- Suggested repair
- Confidence level

### 6. Mechanic booking

After the diagnosis, the user can provide their name, phone number, preferred date, and any additional notes. The booking is stored by Django.

## API Documentation

**Base URL (local development):** `http://127.0.0.1:8000/api`

| Method | Endpoint | Purpose |
|---|---|---|
| `POST` | `/api/chat/` | Send a message, receive the next bot reply |
| `POST` | `/api/upload/` | Upload an image, audio, or video file |
| `POST` | `/api/diagnosis/` | Generate the final AI diagnosis |
| `POST` | `/api/booking/` | Create a mechanic booking |
| `GET` | `/api/booking/<id>/` | Retrieve a booking |
| `GET` | `/api/conversation/<conversation_id>/` | Retrieve a conversation and its messages |

### 1. Chat

`POST /api/chat/`

Sends a user message to the chatbot and receives the next response. For a new conversation, `conversation_id` can be `null` or omitted.

**Request**

```json
{
  "conversation_id": null,
  "message": "My car is overheating."
}
```

For an existing conversation:

```json
{
  "conversation_id": "conversation-uuid",
  "message": "It happens after driving for about 20 minutes."
}
```

**Response**

```json
{
  "conversation_id": "conversation-uuid",
  "bot_reply": "Does the temperature warning light come on?",
  "ready_for_diagnosis": false
}
```

When enough information has been collected:

```json
{
  "conversation_id": "conversation-uuid",
  "bot_reply": "Thanks, that's enough detail for me to work with. Shall I go ahead and put together a diagnosis?",
  "ready_for_diagnosis": true
}
```

### 2. Upload Media

`POST /api/upload/`

Uploads an image, audio file, or video associated with a conversation.

**Content-Type:** `multipart/form-data`

| Field | Description |
|---|---|
| `conversation_id` | ID of the conversation the file belongs to |
| `media_type` | `image`, `audio`, or `video` |
| `file` | The file to upload |

**Example**

```text
conversation_id = 123e4567-e89b-12d3-a456-426614174000
media_type      = image
file            = dashboard-warning.jpg
```

**Response**

Returns the created media upload, including its conversation, media type, file information, and analysis note. For images, the analysis note may contain Gemini's visual observation.

### 3. Generate Diagnosis

`POST /api/diagnosis/`

Generates the final diagnosis using the complete conversation and any available media analysis.

**Request**

```json
{
  "conversation_id": "conversation-uuid"
}
```

**Response**

```json
{
  "summary": "The vehicle may have an issue related to its cooling system.",
  "probable_causes": "Low coolant\nFaulty thermostat\nCooling fan problem",
  "suggested_repair": "Inspect the cooling system and check coolant level, thermostat operation, and radiator fan.",
  "confidence": "medium",
  "used_ai": true,
  "book_recommended": true
}
```

### 4. Create Mechanic Booking

`POST /api/booking/`

**Request**

```json
{
  "conversation_id": "conversation-uuid",
  "customer_name": "John Doe",
  "phone_number": "9876543210",
  "preferred_date": "2026-10-01",
  "notes": "Please contact me after 5 PM."
}
```

**Response**

Returns the created booking with its booking ID and the associated conversation and diagnosis information.

### 5. Get Booking

`GET /api/booking/<id>/`

Retrieves the details of a specific mechanic booking, e.g. `GET /api/booking/1/`.

### 6. Get Conversation

`GET /api/conversation/<conversation_id>/`

Retrieves a conversation and its stored messages.

## Environment Variables

### Backend

Create `backend/.env`:

```env
GEMINI_API_KEY=your_gemini_api_key_here
```

> ⚠️ Never commit your real API key. Share the required variable names through `.env.example` instead:
>
> ```env
> GEMINI_API_KEY=
> ```

### Frontend

Create `frontend/.env.local`:

```env
NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8000/api
```

For production, replace the local URL with your deployed Render backend URL.

## Local Setup

### Prerequisites

- Python 3.10+
- Node.js and npm
- Git

The exact backend package versions are pinned in `backend/requirements.txt` (Django, djangorestframework, django-cors-headers, python-dotenv, google-genai, Pillow, gunicorn, whitenoise), and the frontend packages in `frontend/package.json`.

### Backend

```bash
cd backend

# Create and activate a virtual environment
python3 -m venv venv
source venv/bin/activate        # macOS/Linux
# venv\Scripts\activate         # Windows

# Install dependencies
pip install -r requirements.txt

# Apply migrations and start the server
python manage.py migrate
python manage.py runserver
```

The API is now available at `http://127.0.0.1:8000/api/`.

### Frontend

In a second terminal:

```bash
cd frontend
npm install
```

Create `frontend/.env.local` as described above, then:

```bash
npm run dev
```

The app runs at `http://localhost:3000`.

## Deployment

### Frontend — Netlify

1. Import the GitHub repository into Netlify.
2. Set the **base directory** to `frontend`.
3. Use the build command `npm run build`.
4. Add the environment variable:

   ```env
   NEXT_PUBLIC_API_BASE_URL=<YOUR_RENDER_BACKEND_URL>/api
   ```

The frontend must point at the deployed Render backend, not `http://127.0.0.1:8000/api`.

### Backend — Render

Deploy the Django backend as a Render Web Service using Gunicorn.

| Setting | Value |
|---|---|
| Root directory | `backend` |
| Build command | `pip install -r requirements.txt && python manage.py collectstatic --noinput && python manage.py migrate` |
| Start command | `gunicorn mechanic_backend.wsgi:application` |

Production environment variables:

```env
GEMINI_API_KEY=<your-key>
DEBUG=False
ALLOWED_HOSTS=<your-service>.onrender.com
CORS_ALLOWED_ORIGINS=https://<your-site>.netlify.app
```

The Django deployment should also be configured for production-ready static/media handling and database settings.

> **Note:** SQLite and uploaded media live on Render's local disk, which is ephemeral on the free tier. Data can reset when the service restarts or redeploys. For persistent production data, use PostgreSQL and external media storage.

## Security Notes

- API keys are stored in environment variables.
- `.env` and `.env.local` must not be committed.
- `node_modules/`, Python virtual environments, SQLite runtime files, and generated media should be excluded via `.gitignore`.
- The Gemini API key is never hard-coded into frontend JavaScript.
- Production deployments should use `DEBUG=False`.

## Architecture

The project follows a client-server architecture.

**Frontend (Next.js)** provides the chat interface, message display, media upload controls, diagnosis display, and the mechanic booking modal.

**Backend (Django REST Framework)** provides REST endpoints, conversation management, and persistence for messages, media, diagnoses, and bookings, along with CORS handling.

**Rule engine (`rules.py`)** handles the deterministic conversation logic:

```text
Greeting
   ↓
Car-topic validation
   ↓
Symptom detection
   ↓
Follow-up questions
   ↓
Ready for diagnosis
```

**AI layer (`gemini_service.py`)** handles the Gemini integration. Gemini is intentionally used only for tasks where generative AI is genuinely useful:

```text
Conversation + Media Notes
          ↓
      Gemini API
          ↓
     AI Diagnosis
```

This reduces unnecessary AI requests and keeps the basic conversation flow predictable.
